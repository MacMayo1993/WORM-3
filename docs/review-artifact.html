Status — all findings addressed

Twelve of the fourteen are fixed, tested and driven in a browser to confirm they behave at the real UI. Findings 11 and 13 are large refactors where the concrete harm was fixed and the bulk migration was deliberately left — see their entries. The suite went from 1002 to 1059 tests; lint, build and the bundle gate stay green.

The shape of it

The pure-logic core is genuinely excellent. src/game/ is React-free and DOM-free — verified, not assumed — densely documented with the why rather than the what, and it carries the great majority of the 1002 tests.

The defects cluster almost perfectly in one layer. src/hooks/ holds the orchestration between that pure core and React, contains the 955-line store, is referenced by roughly two test files, and sits outside the coverage report entirely. Every correctness bug below lives there, or in the constant it reaches for.

Three of them are player-visible today at default settings. The seam runs exactly where nobody is looking.

The three that reach the player

01
High

The configurable flip cap is only half-wired

src/game/manifoldLogic.js:206 · src/utils/constants.js:84 · src/hooks/useCubeState.js

The Disparity wizard offers caps of 3 / 8 / 13 / 20, and the store defaults to 8. The chaos sim honours that value. So does the per-tile health bar. So does bet resolution. The player's own flip path does not — it reaches for the module constant: 

// src/game/manifoldLogic.js
const currentFlips = st.flips || 0;
if (currentFlips >= FLIP_CAP) return;        // module constant = 6, not the configured cap
stickers[loc.dirKey] = { ...st,
  curr:  ANTIPODAL_COLOR[st.curr],
  flips: Math.min(FLIP_CAP, currentFlips + 1) };

Verified — 12 consecutive player flips land at flips = 6 regardless of cap

The same constant leaks into presentation, so wormhole pairs sever at 6, the pair-death FX fires at 6, the leaderboard marks tiles dead at 6, and the HUD tooltip prints the wrong number outright — tiles burned out at flip cap (${FLIP_CAP}) reports "(6)" during a cap-13 game.

02
High

Undo of a flip spends two flips of tile life

src/hooks/useUndo.js:62

// Flip is its own inverse — just flip again.

The colour is its own inverse. The flip counter is not — flipStickerPair increments flips on both members of the pair on every call, the undo included.

Verified — board looks restored, a third of the tile's life is gone

Two follow-on effects:

  • On a capped tile the undo is a total no-op — flipStickerPair returns early — yet useUndo still pops history and decrements the move counter. The count drifts below the true number of moves and the history entry is destroyed.
  • WORM³ victory counts stickers with flips > 0, so a flip the player took back still counts as travelled. The secret win can be part-satisfied by retracted moves.
Fix

Undo needs a real inverse, not a repeat. Record flipsBefore for both pair members and restore it, or add an unflipStickerPair that toggles colour while decrementing. Bail out — leaving history and the counter intact — when the flip cannot be reversed.

03
High

Tapping a dead tile charges a move and changes nothing

src/hooks/useCubeState.js:157–193, :275–300

flipSticker guards on three things — the first-flip timer, the refractory window, and first-flip interception. There is no dead-tile guard. When flipStickerPair refuses, the surrounding batch still runs in full: 

cubies: flipStickerPair(...),        // returns the board unchanged
moves: state.moves + 1,             // still charged
moveHistory: [...state.moveHistory, { type: 'flip', ... }],
flipWaveOrigins: origins,  blackHolePulse: ts,
flipPulse: {...},  cubiePops: {...},

A tap on a burnt-out tile plays the sound, pops the cubie, rings the screen glow, charges a move, and pushes an undo entry — while the board does not move. This is the worst failure mode for feedback: the game says "that worked" when nothing happened. It also seeds finding 02's counter drift, since the history now holds an un-undoable entry.

Fix

Return early when the tapped tile or its partner is at the effective cap, and give the refusal its own feedback — a dull thud and a shake read as "this tile is gone", which is information the player needs. The refractory guard is the model to follow.

Input and navigation

04
High

Eight of eleven keyboard callbacks are silently ignored

src/App.jsx:1324–1336 · src/hooks/useKeyboardControls.js:18

App wires up eleven props. The hook destructures two:

// App.jsx — passes 11
useKeyboardControls({
  onMove, onFlip, onUndo, onReset, onShuffle, onSaveState,
  onLoadState, onLevelJump, onExecuteHandsMove, onToggleHandsMode,
  disabled: coopMode,
});

// useKeyboardControls.js — accepts 2
export function useKeyboardControls({ onMove, onFlip }) {

Undo, reset, shuffle, save/load state, level jump and both hands-mode callbacks have no binding at all. There is no Ctrl+Z, despite useUndo being fully implemented.

disabled: coopMode is the live bug. Co-op crawler mode reads WASD and arrows for movement. App tries to disable the cube handler for exactly that reason, and the flag is dropped on the floor — hooks have already run by the time App early-returns into the crawler, so the window listener is still attached. In co-op, WASD drives the crawler and rotates slices of the cube underneath at the same time.

Fix

Honour disabled with an early return, then either implement the remaining shortcuts or delete the dead props. Passed-but-ignored is the worst of the three states — the call site reads as though the feature exists.

05
Medium

The global keydown handler is live on every screen

src/hooks/useKeyboardControls.js:180–222, :308

The listener attaches once at App level with empty deps and guards only three cases: worm-paused, an editable event target, and the level tutorial. Nothing checks the menu, welcome, settings, store, any wizard, help, or victory. So while a full-screen modal owns the display:

  • W A S D Q E rotate slices of the cube behind it
  • C toggles chaos · V cycles visual mode · X explodes the cube · T toggles tunnels
  • arrow keys call preventDefault() unconditionally, blocking arrow-key scrolling inside the settings menu, the store, and the help panel — all scrollable surfaces

A player navigating the menu is silently scrambling their next game.

Fix

Derive one inputTarget from screen state (finding 07) and gate the whole handler on it, rather than adding a guard per new screen.

src/hooks/useKeyboardControls.js:303

Architecture health

07
Medium

A 955-line store, and no screen state machine

src/hooks/useGameStore.js · src/App.jsx:587–622

The store spans roughly twenty domains — cube, session, undo, visual modes, flip FX, chaos, disparity, economy, betting, worm, animation, cursor, UI, levels, hands, dev console, solve, teach, demo, merge, hollow/mirror, face rotation, settings. Only worm is factored out. Zustand's slice pattern is already in the file; it is applied once.

Screen state is ~24 independent booleans with no invariant — ten useState flags in App plus fourteen more in the store. Nothing prevents two being true at once; correctness rests on every handler remembering to clear its peers. That is the root cause of findings 05 and 06: there is no single value to ask what owns the screen right now?

Game modes are non-exclusive booleans too — eleven of them, with getActiveMode resolving conflicts by priority. That is a read-side paper-over, not an invariant: two modes really can be on at once, and the selector just picks one while the other keeps running its effects. The manual patch-ups are already visible — App force-closes Teach Mode when the menu opens or the size leaves 3, because nothing else would.

Fix — incremental, no big bang

Split the store along the section banners already in the file; they are an accurate map, and createWormSlice is the template. Introduce activeScreen as one enum plus a modal stack, and migrate the booleans to derived selectors so call sites need not change at once. Then collapse the mode booleans into a single activeMode, keeping getActiveMode as a shim.

08
Medium

resetGame has drifted from makeDisparityRuntimeDefaults

src/hooks/useGameStore.js:137–150, :338–363

Two hand-maintained lists of the same concept, now unequal:

  • resetGame clears tunnelDeaths; the factory does not.
  • The factory clears disparityParityScore and holonomyMode; resetGame does not — so starting a fresh game carries the previous session's un-cashed parity score forward, and can leave holonomyMode set.

Smaller drift in the same file: a comment names makeWormRuntimeDefaults, which does not exist; clearDisparityGame lives in the worm slice despite its name; visualMode's comment lists four modes while cycleVisualMode cycles nine; and victory/achievedWins still carry sudokube and ultimate, whose screens were removed.

Fix

resetGame should spread makeDisparityRuntimeDefaults() and add only genuinely session-scoped fields, with tunnelDeaths moved into the factory beside the other transient FX maps it already owns.

What changed

The store — the monolith these fixes actually had to work inside — went from 955 lines to a 122-line assembly over ten slices, none larger than 156. Worth doing against a screenshot baseline, as its own piece of work.

Interface and accessibility

12
Medium

Six card-button families have no focus ring

Corrected from the first draft of this review, which claimed focus styling was absent app-wide. It is not: App.css has carried a global button:focus-visible, [role='button']:focus-visible rule all along, and it covers the great majority of the app's 220 buttons.

The real defect is narrower and sharper. Six components set outline: 'none' inline, and an inline style beats any stylesheet selector on specificity — so the global rule never applied to them. Those six are the setup wizard cards, the shared wizard step cards, the tile style and scene pickers, cube mode select, and coming soon: the primary interactive surface of the entire pre-game flow, with no keyboard focus indicator at all.

Form controls were genuinely uncovered too — input, select and textarea had only two bespoke :focus rules between them.

Fixed

Removed the six inline outline: 'none' declarations so the global rule reaches them; tap-flash suppression stays on -webkit-tap-highlight-color, which does not touch keyboard focus. Extended the rule to links, inputs, selects, textareas and [tabindex], with a comment recording why an inline outline breaks it.

13
Low

995 inline style objects against 4.6k lines of CSS

Concentrated in TeachMode (80), ParityStoreScreen (52), WormCrawlerHUD (49), DisparityBettingScreen (43). Each is a fresh object per render, defeating React.memo on any component receiving one as a prop, and none can express :hover, :focus, :active or media queries.

The token layer is in good shape — uiTheme.js is well designed and imported by 61 files — and a shared primitive layer already exists in src/components/ui/ (Panel, Button, useDialogBehavior), whose own comments describe exactly this problem. Only seven screens have adopted it.

What changed

The concrete harm — six card-button families with no keyboard focus ring — is fixed under finding 12. The remaining work is migrating roughly twenty screens onto primitives that already exist, which is a visual change to most of the game's surface area; it wants a screenshot baseline and a human eye on the result rather than a blind sweep. The inline count is a symptom worth tracking, not a defect to clear in one pass.

CLAUDE.md has drifted from the tree it describes

  • The UI-theme note documents GLASS_* as the "dark navy in-game overlay family". Those tokens no longer exist — uiTheme.js explicitly records the glass family's removal in favour of NIGHT_*. An agent following the doc today would import symbols that are gone.
  • The directory tree omits five real directories: coming-soon/ (12 files), holonomy/ (5), modes/ (5), workers/ (1), assets/.

What is working well

Worth stating plainly, because it is much of why this codebase is pleasant to review.

  • The purity of src/game/ is real, not aspirational. Zero React imports, zero DOM access — verified by grep. It is why every bug above was reproducible in a five-line test.
  • The comments explain the why. Why non-slice cubies keep their references (React.memo and InstancedMesh colour-buffer corruption); why incremental map rebuilds are safe; why the live win path skips detectWinConditions. This is unusually good.
  • The March review's recommendations were genuinely executed. Wizard duplication is gone behind a shared WizardChrome and wizardSteps/; shaders are extracted; HealerWormMode dropped from 2041 lines to 526.
  • Performance work is thoughtful and measured — worker-based chaos, incremental grid maps, adaptive DPR with a separate Mega override, frameloop parking on tab hide, and a ClockContinuity component to keep timelines unbroken across it.
  • Bundle discipline holds — vendor chunks separated, heavy modes lazy-loaded, and a bundle:check gate wired into CI.
